# White-label e-commerce platform

Multi-tenant storefronts on one platform: an ASP.NET Core API, an Angular storefront rendered on the server (SSR), and an Angular admin. Planning documents are in [`docs/`](docs/); the plan of record is [`docs/roadmap.md`](docs/roadmap.md).

**Status:** milestone M0 (walking skeleton). There are no business features yet: one store page shows the API status fetched during server rendering, and the admin shows a placeholder.

| Path | Content |
|---|---|
| `backend/` | .NET 10 solution: `Api`, `Cli`, `AppHost` (local orchestration), modules, tests |
| `frontend/` | Angular workspace: `storefront` (SSR), `admin`, libraries, E2E tests ([README](frontend/README.md)) |
| `contracts/` | `openapi.json` (generated by the API build) and shared test vectors ([README](contracts/README.md)) |
| `dev/` | Local edge (`caddy/Caddyfile`) and PostgreSQL bootstrap script |
| `scripts/` | Repository checks (browser bundle scan) |

| Tool | Version | Pinned by |

| Container runtime | Docker Desktop, or Docker Engine / Podman with Docker compatibility | — |

Port **443** must be free: the local edge serves `https://*.localhost` there.

## Start the local stack

From a fresh clone:

```bash
cd frontend && npm ci && cd ..
dotnet run --project backend/src/AppHost
```

The AppHost prints the Aspire dashboard URL and starts PostgreSQL, the API, the storefront and admin dev servers, and the local edge (Caddy). On first start it generates the database role passwords and the three trusted-path keys and keeps them in the AppHost's user secrets (never in the repository).

| URL | What |
|---|---|
| `https://brand-a.localhost/` | Storefront (server-rendered; shows the API status). `brand-b.localhost` is a second development store. |
| `https://admin.localhost/` | Admin placeholder |
| `https://<either host>/api/health` | API, same origin |

Requests go only through the edge. The API and the SSR server reject direct requests (`403`) because they lack the keys the edge adds ([ADR-04](docs/architecture-decisions.md#adr-04-request-topology-host-resolution-and-public-caching)).

### Trust the local certificate (once)

The edge uses its own local certificate authority, kept in the `platform-edge-data` volume. After the first start, export its root certificate and trust it:

```bash
docker run --rm -v platform-edge-data:/data alpine cat /data/caddy/pki/authorities/local/root.crt > caddy-local-root.crt
```

- Windows: `certutil -user -addstore Root caddy-local-root.crt`
- macOS: `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain caddy-local-root.crt`
- Linux (Debian/Ubuntu): `sudo cp caddy-local-root.crt /usr/local/share/ca-certificates/ && sudo update-ca-certificates`; Firefox and Chrome on Linux may need it imported in their own certificate settings.

Delete `caddy-local-root.crt` afterwards. Removing the volume creates a new authority, which must be trusted again.

## Configuration and secrets

Every process validates its settings on start and refuses to start with missing or invalid values, naming the setting and never printing its value.

| Process | Settings | Example |
|---|---|---|
| API | `ConnectionStrings:platform`; `TrustedPath:ApiEdgeKey`, `TrustedPath:SsrApiKey` (each with an optional `…Previous` for rotation), `TrustedPath:EdgeNetworks`, `TrustedPath:SsrNetworks` (CIDR ranges) | Set by the AppHost |
| SSR server | `PLATFORM_SSR_INGRESS_KEY`, `PLATFORM_SSR_API_KEY`, `INTERNAL_API_BASE_URL` | [`frontend/projects/storefront/.env.example`](frontend/projects/storefront/.env.example) |
| Edge | `PLATFORM_API_EDGE_KEY`, `PLATFORM_SSR_INGRESS_KEY`, upstream URLs | [`dev/caddy/Caddyfile`](dev/caddy/Caddyfile) |

Each process holds only its own keys: the SSR server never gets the API edge key, and the API never gets the SSR ingress key. Startup fails if either is supplied.

## Continuous integration and branch protection

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every pull request and on pushes to `main`. Its job names are the required status checks:

- `Backend build and tests`
- `Frontend lint, tests, and builds`
- `Contract drift check`
- `E2E through the local edge`
- `Secret scan`

Branch protection on `main` (G3, M0-17):

| Step | Status |
|---|---|
| Base rules: pull request required (0 approvals, solo developer), no direct or force pushes, no deletion | Configured and verified 2026-10-19 |
| The five checks above added as required status checks | **Pending: the repository owner records the date here once configured** |

Dependency updates arrive as Dependabot pull requests ([`.github/dependabot.yml`](.github/dependabot.yml)) and pass the same checks.
